El modelo y el método van en la URL. La API externa exige plan Custom, que es el contratado. Las API keys de Odoo caducan (máximo tres meses): la rotación entra en el diseño desde el principio.

i La regla que evita la mayoría de los errores

La API recibe nombres técnicos e IDs, no las etiquetas de la pantalla. Se envía partner_id: 123, nunca "Cliente": "ACME". Igual con diario, moneda e impuestos.

02Crear una factura de cliente

POST /json/2/account.move/create
{
  "vals_list": [{
    "move_type": "out_invoice",
    "partner_id": 123,
    "journal_id": 7,
    "invoice_date": "2026-09-10",
    "currency_id": 1,
    "invoice_date_due": "2026-10-10",
    "invoice_line_ids": [
      [0, 0, {
        "name": "Servicio mensual",
        "quantity": 1,
        "price_unit": 250000,
        "tax_ids": [[6, 0, [21]]]
      }]
    ]
  }]
}
DetallePor qué
vals_listEs el argumento de create(vals_list): una lista de diccionarios.
[0, 0, {…}]Triple literal que crea una línea. Por RPC no se usan los Command de Python.
[[6, 0, [ids]]]Comando 6: fija el conjunto de una Many2many. Los impuestos van así, no como lista plana.
! Nace en borrador

La factura queda en draft y no tiene efecto contable hasta contabilizarla con action_post.

      [0, 0, {"name": "Compra de equipo", "quantity": 2,
              "price_unit": 800000, "tax_ids": [[6, 0, [21]]]}]
    ]
  }]
}

ref es el número que entrega el proveedor. No es el número interno de Odoo: son dos cosas distintas y conviene no mezclarlas.

Secuencia de producción

el orden importa
  1. Leer /doc de la base
  2. Resolver maestros y cachear IDs
  3. Validar fechas, moneda y líneas
  4. create
  5. Revisar el borrador
  6. action_post
  7. Verificar state, name, payment_state
  8. Ante error: guardar respuesta e ID. No reintentar a ciegas

Resolver los IDs

search_read
POST /json/2/res.partner/search_read
{
  "domain": [["name","ilike","ACME"]],
  "fields": ["id","name","vat"],
  "limit": 10
}

Igual para account.journal (type=sale), res.currency y account.tax. Cachear: no asumir IDs.

! Dos formas del payload circulan por ahí

Esta guía usa {"vals_list": [{…}]}, coherente con /json/2/, donde modelo y método ya van en la URL. Circula otra variante con envoltura jsonrpc/kwargs/fields, que corresponde al RPC clásico (/web/dataset/call_kw).

No se verificó contra una base real. Confirmar en /doc antes de codificar — y de paso los nombres exactos de los campos l10n_co_dian, incluida la caja del CUFE.

Integración DIAN

De dónde partimos y qué se puede automatizar

✓ El punto de partida es bueno ya funciona

La facturación electrónica y el documento soporte ya operan contra la DIAN desde Odoo. La suscripción Custom ya habilita JSON-2.

Lo que sigue no reemplaza esa conexión: añade una capa de sincronización y control encima. Riesgo bajo.

08La arquitectura

Si Make no puede con alguna operación SOAP, se intercala un microservicio DIAN pequeño. Eso se decide después del test, no ahora.

! Contabilizar no es emitir

action_post contabiliza el asiento en Odoo. No emite ante la DIAN: de eso ya se encarga la conexión existente.

Servicios DIAN

consulta
  • GetStatus — estado del documento
  • GetStatusZip — estado de lote
  • GetXmlByDocumentKey — XML por CUFE/CUDE
  • GetNumberingRange — rangos y resoluciones
  • GetTaxPayer — datos del contribuyente

Son SOAP con WS-Security y certificado, no REST con API key.

Los 8 módulos

complejidad
  • media Estado DIAN de facturas
  • media Descarga de XML
  • media Control de resoluciones
  • media Sincronización de estados
  • media Monitor automático
  • alta Facturas de proveedor
  • alta Eventos electrónicos
  • muy alta RADIAN

Los de complejidad media son el núcleo y se pueden abordar primero. RADIAN es otro proyecto: no se mezcla con el arranque.

Decisión

Un test antes de construir nada

Test de viabilidad

3 pasos
  1. Make lee una factura en Odoo por JSON-2
  2. Make consulta GetStatus con un CUFE real
  3. La respuesta vuelve y actualiza esa factura en Odoo

Si los tres pasan, la arquitectura completa queda demostrada y el resto se construye por módulos.

Qué hace falta

para correrlo
  • Endpoint DIAN de producción que la empresa puede usar
  • Certificado y credenciales
  • Un CUFE real de una factura ya emitida
  • El campo de Odoo donde escribir el estado — confirmar en /doc
